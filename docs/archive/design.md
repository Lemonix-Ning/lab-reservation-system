《基于规则配置的高校实验室资源预约与调度管理系统》

现在进行项目阶段汇总 只保留项目目前文档，
开发日志只记录错误和解决方案。其余文档全部删除

当前实现采用 Node.js + React + tRPC 全栈方案，业务需求与原始规划一致，但技术栈由 Java/RuoYi 演进为 TypeScript 全栈实现。

一、项目总体说明
1.1 项目背景
随着高校实验教学和科研活动的增加，实验室和实验设备成为重要的稀缺资源。传统的纸质登记、QQ群/微信群预约方式存在以下问题：

预约流程不规范，容易产生冲突与纠纷；
实验室使用情况无法量化统计，管理者难以决策；
预约规则分散在人工通知中，缺乏统一配置与约束；
缺少对实验室资源的整体调度与数据分析能力。
因此，设计并实现一套基于 Web 的实验室资源预约与调度管理系统，能够为师生提供标准化的在线预约服务，为管理者提供可视化的数据决策支持，具有现实意义和工程实践价值。

1.2 设计目标
本系统的目标：

实现实验室和设备的统一信息管理与分类维护；
提供在线预约与审批流程，支持基本的冲突检测；
支持可配置的预约规则（次数限制、时间段限制等），增强系统灵活性；
提供实验室使用率、预约情况的统计分析与可视化展示；
通过合理的架构与技术选型，体现良好的可扩展性和可维护性。
1.3 用户角色与使用场景
普通学生用户（Student）

浏览实验室信息；
发起实验室预约申请；
查看个人预约记录及状态。
教师/实验指导老师（Teacher，可选）

以团队/课程为单位发起预约；
审核本课程相关的预约需求（可视情况实现）。
实验室管理员（LabAdmin）

维护实验室、设备信息；
审核并处理预约申请；
管理预约规则与黑名单。
系统管理员（SysAdmin）

用户、角色、菜单等系统级管理；
监控系统运行情况，维护系统参数。
二、需求分析
2.1 功能需求
2.1.1 用户与权限管理
用户登录、退出；
角色管理：普通学生用户（user）、实验室管理员/系统管理员（admin）；
权限控制：基于角色的接口访问控制和前端菜单显示控制。

实现方式（当前方案）：
- 通过 OAuth 登录（OAuth），在后端统一接入登录流程；
- 使用 `users` 表（字段：id、openId、name、email、loginMethod、role 等）存储用户基础信息和角色；
- 通过 tRPC 中间件在服务端进行角色鉴权，限制仅管理员可访问实验室管理、预约审批、统计等管理接口；
- 前端根据当前登录用户的 `role` 字段动态控制导航菜单和页面访问（普通用户仅能访问预约相关页面和个人记录）。

2.1.3.1 实验室与设备资源管理增强（P1）

**现状总结**：

当前已实现的设备管理能力：
- 字段支持：设备编号（deviceNo）、名称、类型、采购日期、状态（normal/maintenance/retired）、备注
- 关联关系：设备与实验室的一对多关联（labId 外键）
- 操作能力：增删改查、按实验室筛选、状态过滤
- 前端页面：设备管理、设备列表、设备详情展示

**开放规则配置**（文档层面设计）：

实验室需要支持灵活的开放时间配置，以适应不同的运维要求：

| 规则维度 | 配置方式 | 说明 |
|---------|--------|------|
| **工作日** | 开始时间 + 结束时间 | 默认：08:00 - 22:00，管理员可修改 |
| **周末** | 开始时间 + 结束时间 | 默认：同工作日，管理员可单独配置或关闭 |
| **节假日** | 启用 / 关闭 + 自定义日期范围 | 选择特定日期为节假日，设定该日期是否开放 |
| **默认行为** | 级联规则 | 无特殊配置 → 按工作日规则；有节假日配置 → 优先级：节假日 > 工作日/周末 |

**维护期与禁用时段**（文档层面设计）：

为了支持实验室和设备的维护管理，系统需要支持"禁用时段"配置：

| 禁用对象 | 时段设置 | 对现有预约的处理 | 对新预约的处理 |
|---------|--------|--------------|------------|
| **整个实验室** | 开始时间 + 结束时间 + 维护原因 | 显示风险提示，可选强制取消（需管理员操作） | 禁止创建新预约，显示"维护中"提示 |
| **单个设备** | 开始时间 + 结束时间 + 设备 ID | 预约可继续进行，但显示"关键设备不可用"提示 | 预约表单中禁用该设备选项，显示灰化说明 |
| **多个设备** | 选中多个设备的批量禁用 | 同上，提示具体哪些设备不可用 | 同上，禁用对应选项 |

**场景示例 1：实验室因维护一周关闭**

```
背景：某计算机实验室因升级网络设备，需要维护 7 天（2025-12-15 至 2025-12-21）。

操作步骤：
1. 管理员在"禁用时段"页面新增记录：
   - 实验室：计算机实验室 A
   - 开始时间：2025-12-15 08:00
   - 结束时间：2025-12-21 22:00
   - 原因：网络设备升级维护
   - 处理策略：自动警告现有预约，由学生/教师决定是否取消

2. 系统自动行为：
   - 已通过的预约（跨越禁用时段）：显示"⚠️ 预约时段重叠维护期，请尽快确认是否调整"的提示
   - 新的预约申请：在禁用时段内无法创建，前端显示"该实验室暂未开放，维护期至 2025-12-21"
   - 已拒绝/已取消的预约：无影响，仅记录维护期信息用于日后追查

3. 维护结束后：管理员标记禁用时段为"已结束"，系统恢复正常预约
```

**场景示例 2：某台设备故障暂停使用**

```
背景：物理实验室的示波器故障，预计维修 3 天（2025-12-12 至 2025-12-14）。

操作步骤：
1. 管理员在"设备管理"页面修改该设备状态 → "maintenance"（维修中）
   或在"禁用时段"新增：
   - 禁用对象：单个设备（示波器 SN:001）
   - 开始时间：2025-12-12 08:00
   - 结束时间：2025-12-14 22:00
   - 原因：设备故障维修

2. 系统自动行为：
   - 预约表单：该设备灰化显示，无法选中，提示"示波器维修中，恢复时间：12 月 14 日"
   - 现有预约：
     - 若预约中包含该设备且时间重叠 → 显示"🔴 关键设备不可用"提示，预约可继续但风险标记
     - 学生可选择调整预约时间或取消
   - 预约可以继续进行，但用户需知晓该设备不可用

3. 维修完成后：
   - 管理员修改设备状态 → "normal"（正常）
   - 系统恢复该设备可选，无需修改预约
```

2.1.4 预约管理模块（核心）
学生预约流程：

学生登录后选择实验室；
选择预约日期与时间段（开始时间、结束时间）；
填写预约事由、预计人数等信息；
提交预约申请，进入“待审核”状态。
审批流程（实验室管理员）：

查看待审核预约列表；
检查预约时间是否合理，有无冲突；
审核通过则标记为“已通过”，拒绝则标记为“已拒绝”，可填写拒绝原因。
预约状态管理：

状态：待审核、已通过、已拒绝、已取消、已完成；
学生可以在预约未审核前主动取消；
预约到期后可自动标记为“已完成”（定时任务）。
冲突检测（基础版）：

同一实验室在同一时间段内，仅允许一个“已通过/待审核”的预约；
新预约提交时，对指定实验室进行时间重叠检测，若有冲突则拒绝提交。
2.1.5 预约规则与策略配置模块（亮点）
配置内容：

每位学生每日/每周最多可预约次数；
单次预约时长上限（如 4 小时）；
提前预约时间限制（如必须提前至少 1 天）；
特殊时间段限制（如期末周开放到晚上 10 点）。
配置方式：

在后台系统中以界面形式进行配置；
规则数据存储于数据库配置表，支持动态修改，无需重启系统。
应用方式：

在提交预约之前，系统根据当前规则进行检查，若不满足条件，则给出明确提示。

2.1.6 审批流程配置模块（新增）

本系统的"发起人"与"审批节点"需要明确区分，以避免流程理解的歧义。

**概念定义**：

| 概念 | 说明 |
|------|------|
| **发起人** | 创建预约的用户角色（Student / Teacher / Admin），其创建动作代表"已同意" |
| **审批节点** | 系统内需要进行的实际审批环节（可能是LabAdmin、Dept等），与发起人角色无关 |
| **审批级别** | 需要经过的审批节点数（0/1/2/3级），仅描述节点数，不与具体角色绑定 |

**审批级别定义**：

- **0级（自动通过）**：预约创建后直接进入已通过状态，无需任何审批。
- **1级（单级审批）**：预约创建后进入一个审批节点审批（当前实现为实验室管理员）。
- **2级（两级审批）**：预约经过两个审批节点（如教师/院系 → 实验室管理员）。
- **3级（三级审批）**：预约经过三个审批节点（如教师 → 院系 → 实验室管理员）。

**课程预约特殊处理**：

- 当教师（作为发起人）创建课程预约时，教师的"审批意见"已隐含在发起预约的动作中，不再作为单独的系统审批节点。
- 因此，课程预约的实际审批流程从配置的**第一级**开始。
- 示例：如配置为"2级审批（教师 → 管理员）"，课程预约会跳过"教师审批"步骤，直接进入"管理员审批"。

**配置方式**：

- 在后台"审批配置管理"页面，管理员可选择"全局默认"或"特定实验室"配置。
- 支持同时配置"改签窗口"（预约开始前多少小时内禁止修改）、"最大改签次数"等规则。
- 所有配置即时生效，无需重启系统。

3.4 系统层次结构设计

本系统采用典型的前后端分离 + 类型安全 RPC 架构，后端为 Node.js + TypeScript，前端为 React + TypeScript。

后端层次结构：
- 接口层：tRPC Router（集中在 `server/routers.ts` 及各业务路由文件），对外暴露类型安全的远程调用接口；
- 业务逻辑层：各业务 Router 内部的 handler 以及 `server/_core` 中的业务服务（如预约规则校验、冲突检测、统计聚合）；
- 数据访问层：基于 Drizzle ORM 的数据表定义与查询（位于 `drizzle/schema.ts`，通过 `server/db.ts` 注入）；
- 基础设施层：统一配置、环境变量、日志、OAuth、AI 服务封装等（位于 `server/_core` 目录）。

前端层次结构：
- 页面层：位于 `client/src/pages`，如 `Home`、`LabRoomList`、`LabDashboard`、`MyReservations`、`StatisticsDashboard` 等，负责具体业务页面；
- 组件层：位于 `client/src/components`，包括 `DashboardLayout`、`AIChatBox` 以及基于 shadcn/ui 的通用 UI 组件；
- 状态与逻辑层：自定义 Hooks（如 `useReservationRules`、`useMobile`）、上下文（如 `ThemeContext`）等；
- 通信层：`client/src/lib/trpc.ts` 中封装 tRPC 客户端，结合 TanStack Query 进行数据获取与缓存管理。
四、数据库设计
以下为核心业务表的设计，已经在项目中通过 Drizzle ORM 的 `drizzle/schema.ts` 文件落地实现。字段命名采用 camelCase，并与 TypeScript 类型保持一致。

4.1 实验室信息表 `lab_rooms`
- id：主键，自增 int
- roomNo：实验室编号（唯一），varchar(50)
- name：实验室名称，varchar(100)
- building：所在楼宇，varchar(100)
- location：具体位置（如“信息楼 3 楼 305”），varchar(200)
- capacity：可容纳人数，int，默认 0
- type：实验室类型（机房、化学等），varchar(50)
- managerId：负责人用户 ID（关联 `users.id`），int
- openTimeStart：日常开放开始时间（如 "08:00"），varchar(10)
- openTimeEnd：日常开放结束时间（如 "22:00"），varchar(10)
- status：状态，enum("enabled", "disabled")，默认 "enabled"
- remark：备注，text
- createdAt：创建时间，timestamp
- updatedAt：更新时间，timestamp

该表用于支撑实验室列表展示、条件查询以及后台管理维护。

4.2 设备信息表 `lab_devices`
- id：主键，自增 int
- labId：所属实验室 ID（关联 `lab_rooms.id`），int
- deviceNo：设备编号，varchar(50)
- name：设备名称，varchar(100)
- type：设备类型，varchar(50)
- purchaseDate：采购日期，timestamp
- status：状态，enum("available", "maintenance", "retired")，默认 "available"
- description：简介，text
- createdAt：创建时间，timestamp
- updatedAt：更新时间，timestamp

该表用于实现设备与实验室的一对多关联，为后续设备级预约或维护记录提供基础。

4.3 预约主表 `lab_reservations`
- id：主键，自增 int
- labId：实验室 ID（关联 `lab_rooms.id`），int
- userId：预约人 ID（关联 `users.id`），int
- title：预约标题（如“数据结构课程实验”），varchar(200)
- reason：预约事由说明，text
- peopleCount：预计人数，int，默认 1
- startTime：预约开始时间（精确到日期+时间），timestamp
- endTime：预约结束时间，timestamp
- status：预约状态，enum("pending", "approved", "rejected", "cancelled", "completed")
- rejectReason：拒绝原因（可空），text
- applyTime：提交申请时间，timestamp
- approveTime：审核时间，timestamp，可空
- createdAt：创建时间，timestamp
- updatedAt：更新时间，timestamp

该表记录完整的预约生命周期，配合业务逻辑实现状态流转与冲突检测。

4.4 预约规则配置表 `lab_reserve_rules`
- id：主键，自增 int
- ruleCode：规则编码（如 "MAX_PER_DAY"、"MAX_DURATION"、"ADVANCE_DAYS" 等），varchar(50)，唯一
- ruleName：规则名称，varchar(100)
- ruleValue：规则值（字符串形式，便于灵活解析，如 "3"、"4h" 等），varchar(100)
- description：规则说明，text
- status：状态，enum("enabled", "disabled")，默认 "enabled"
- createdAt：创建时间，timestamp
- updatedAt：更新时间，timestamp

系统在提交预约之前会查询启用状态的规则，并对用户当日/当周预约次数、单次预约时长、提前预约天数等进行统一校验，实现“基于规则配置的预约限制”。

4.5 用户信息表 `users`
- id：主键，自增 int
- openId：OAuth 返回的用户唯一标识，varchar(64)，唯一
- name：用户姓名，text
- email：邮箱地址（可选），varchar(320)
- loginMethod：登录方式标识（如 manus），varchar(64)
- role：角色，enum("user", "admin")
- createdAt：创建时间，timestamp
- updatedAt：更新时间，timestamp
- lastSignedIn：最近登录时间，timestamp

该表支撑 OAuth 登录、角色区分以及后续的权限控制、统计分析等功能。

4.6 预约统计表（可选扩展）
当前版本通过实时 SQL 统计获取预约次数、使用时长等数据，暂未单独建立统计中间表；
如需支持更复杂的报表和历史分析，可扩展设计 `lab_usage_stat` 等离线统计表，按日/周维度汇总实验室使用数据（实验室 ID、日期、总预约时长、预约次数等）。

五、关键业务流程设计
5.1 用户登录与权限控制流程
系统基于若依的登录模块：
用户输入账号密码 → 后端验证 → 生成 Token → 前端保存 Token 并携带访问接口。
权限控制基于角色与菜单：
学生只能访问预约申请与个人记录页面；
管理员可访问实验室管理、规则配置、审核页面。
5.2 实验室预约流程
学生登录系统；
进入“实验室预约”页面，选择实验室、日期和时间段，填写事由等信息；
系统在提交前执行两类校验：
是否满足预约规则（次数、时长、提前时间等）；
是否与已存在的预约冲突（时间段重叠检测）；
若校验通过，创建预约记录，状态设为“待审核”；
实验室管理员登录后台，查看待审核列表；
管理员根据情况选择“通过”或“拒绝”，并记录拒绝原因；
学生端可查看预约状态变化，若预约到期后由定时任务自动标记为“已完成”。
5.3 时间段冲突检测逻辑
判断新预约 [start_new, end_new] 与已存在预约 [start_exist, end_exist] 是否有重叠，可使用以下逻辑：

不重叠的条件：
end_new <= start_exist 或 start_new >= end_exist
有重叠的条件：
否定以上条件，即：
not (end_new <= start_exist or start_new >= end_exist)
SQL 查询示意（MySQL）：

查询某实验室在指定时间段内是否存在“已通过/待审核”的预约记录。
你可以在 Service 层抽象出一个工具方法，专门处理时间段冲突检测，便于单元测试和维护。

5.4 预约规则检查流程
提交预约时：

查询当前全局规则配置（如：每日最大次数、每周最大次数、单次时长上限等）；
统计当前用户在当天/当周的已存在预约记录；
对比规则值，若超出限制则返回明确错误提示；
若规则表中某项未启用，则跳过该规则检查。
六、接口设计示例（tRPC / REST API）

6.1 实验室管理
- `lab.listRooms`：查询实验室列表（支持分页、条件查询：楼宇、类型、状态等）；

- `lab.updateRoom`：修改实验室（管理员）；

- `device.listDevices`：按实验室或条件查询设备列表；
- `device.createDevice`：新增设备（管理员）；
- `device.updateDevice`：修改设备信息；
- `device.deleteDevice`：删除设备。

- `reservation.create`：学生发起预约申请，请求体包括 labId、startTime、endTime、reason、peopleCount 等；

- `stat.statusDistribution`：查询预约状态分布（用于饼图展示）；
- `stat.trend`：按时间维度统计预约趋势（用于折线/面积图）；

  - 外键：`labId` 关联 `lab_rooms.id`；
  - 表示实验室中具体的设备信息，为设备管理和后续设备级预约扩展提供基础。

综合上述实体及关系，可以在 ER 图中清晰展示：
- `users` 与 `lab_reservations` 的一对多关系；
- `lab_rooms` 与 `lab_reservations` 的一对多关系；
- `lab_rooms` 与 `lab_devices` 的一对多关系；
- `lab_reserve_rules` 作为全局配置实体与预约业务的间接关联。

## 三、核心实现细节

### 3.1 预约完整业务流程

预约验证包括 6 个步骤：基础验证  冲突检查  规则引擎  黑名单检查  创建预约  审批流程

### 3.2 预约规则引擎（lab_reserve_rules）

三个核心规则：MAX_PER_DAY（每日最多 3 次）、MAX_DURATION（单次最长 4 小时）、ADVANCE_DAYS（提前 7 天）

### 3.3 审批流程配置

区分发起人（Student/Teacher）与审批人（labAdmin/sysAdmin），支持 0-3 级审批

### 3.4 改签规则

默认 24 小时窗口，最多 3 次改签

### 3.5 违约与黑名单

4 种违约类型，累计 10 分自动黑名单

### 3.6 审计日志

20+ 集成点，记录所有关键操作

### 3.7 角色权限矩阵

| 角色 | 权限 |
|-----|------|
| Student | 个人预约操作 |
| Teacher | 课程管理 |
| LabAdmin | 审核预约 + 规则配置 |
| SysAdmin | 所有权限 |
